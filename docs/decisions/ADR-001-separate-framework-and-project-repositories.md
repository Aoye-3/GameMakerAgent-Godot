# ADR-001：框架仓库与游戏项目仓库保持独立

## 状态

Accepted

## 日期

2026-08-31

## 背景

GameMakerAgent 需要在 TapTap GameJam 的真实项目推进中快速迭代，同时保留长期
可迁移性。如果框架与游戏代码共处一个仓库，项目特定的玩法、资产和时间压力会
逐渐污染通用接口；如果框架脱离项目独立设计，又会产生没有被实际制作验证的抽象。

## 决策

1. `Aoye-3/GameMakerAgent` 是可复用开发框架的权威仓库。
2. `Aoye-3/TapTapGameJam` 是具体 Godot 游戏项目的权威仓库。
3. 新能力先在项目内解决真实问题，随后通过测试、运行证据、Reviewer 和人工审批
   才能晋升到 GameMakerAgent。
4. 两个仓库各自维护 Doc 体系；框架文档与项目文档不能共用同一事实入口。
5. 两仓不使用 Git 子模块、不提交本机绝对路径，也不通过复制整仓保持同步。

## 备选方案

### 单一仓库

便于初期修改，但会混合发布节奏、文档事实和所有权，拒绝。

### 框架优先、项目只消费发布版本

边界清晰，但 GameJam 阶段会阻碍从项目快速反馈，拒绝。

### 项目优先、结束后一次性抽离

短期最快，但最后通常无法辨认通用能力与项目偶然实现，拒绝。

## 后果

- 需要明确的 Promotion Manifest 和跨仓库来源记录。
- 项目可以快速试错，框架只承担通过门禁的稳定能力。
- 同一概念可能短期存在项目候选和框架稳定版，必须使用版本与状态区分。
- 跨仓变更需要分别提交和审查，不能假设一个提交同时覆盖两边。
